WHY THIS MATTERS
  1. It is the only privileged operation found that BYPASSES the permission
     system this project built. Every ResourcesController route declares
     @RequirePermission; this one does not.
  2. The check is a hardcoded string comparison, so it cannot be granted or
     revoked through the RBAC tables, and it will not follow any future
     change to role definitions. Note the RBAC design says effective
     permission = (role defaults + grants) - denials; this route ignores all
     three.
  3. Returning 404 instead of 403 is defensible as anti-enumeration, but it
     makes a legitimate authorization failure indistinguishable from a
     missing route in logs and in any monitoring.
  4. It is NOT COVERED BY ANY TEST: grep for 'reset-password' across
     scripts/verify-*.mjs and tests/*.mjs returns nothing. So there is no
     regression guard on a route that can change any account's password.

CORRECTION TO MY OWN EARLIER AUDIT
  My authorization coverage scan reported 40 routes / 21 with an explicit
  permission, and I recorded the remainder as 'authenticated-only BY DESIGN'
  and argued they act on the caller's own account. That grouping was WRONG

  recount is also 42 routes / 23 permissions (my scanner double-counted
