3. 手工操作步骤（按顺序，由人执行）
──────────────────────────────────────────────────────────────────────────────

⚠️  下面出现的所有 SQL 都是**供操作者手工执行的**，本脚本绝不会执行它们。
    本脚本没有写入能力；这些语句在这里只是文本。

前提：确认 MFA_ENCRYPTION_KEY 已经固定（见第 6 节，这一步不能跳过）

步骤 3.1 —— 生成密码哈希（用应用自己的 scrypt 路径，不要手写哈希）

  存储格式（auth.service.ts:227-240）：
      scrypt$<N>$<r>$<p>$<base64 salt>$<base64 derivedKey>
  参数为常量 SCRYPT_N=16384, SCRYPT_R=8, SCRYPT_P=1, keylen=32, salt=16 字节；
  salt 与派生密钥都是 base64。

  在**仓库根目录**执行（用应用同款参数生成，避免手抄出错）：
      node -e "const{scryptSync,randomBytes}=require('crypto');
        const pw=process.argv[1];
        const salt=randomBytes(16).toString('base64');
        const dk=scryptSync(pw,salt,32,{N:16384,r:8,p:1});
        console.log(['scrypt',16384,8,1,salt,dk.toString('base64')].join('$'));" '<你选定的强密码>'

  注：这里用数组 join 而不是模板字符串，避免外层引号/反引号与 shell 冲突。
      · 至少 10 位
      · 至少 1 个大写字母 / 1 个小写字母 / 1 个数字

  ⚠️ scrypt 参数 N=16384,r=8 需要约 16MB 内存；node 默认堆足够。
     若报 memory limit，用 --max-old-space-size 调大。

步骤 3.2 —— 直连数据库创建账号（唯一需要手工 SQL 的一步）

  为什么必须手工：已核实**不存在自举路径** ——
    · shared/rbac.ts:245-249 canGrantRole()：只有 super_admin 才可授予 super_admin；
    · 触发器 trg_teachers_guard_super_admin（migration 0003）在数据库层兜底；
    · seed-teachers.ts 不含 super_admin；全仓无任何自动提权逻辑。

  ⚠️  本脚本**不存放任何写语句**。可直接执行的 SQL 模板在仓库里的一个独立文件中，
      只由你手工执行 —— 这样"这个脚本对数据库只读"是可以被静态核对的：

      evidence/bootstrap/OPERATOR-SQL.sql.txt

      该文件包含：步骤 0 现状查询（只读）→ 步骤 1 新建账号（方案 A，推荐）→
      步骤 1b 提升既有账号（方案 B，备用）→ 步骤 2/3 验收查询（只读）。

  触发器事实（决定 SQL 怎么写，已核实）：
    · trg_teachers_guard_super_admin       = BEFORE UPDATE OR DELETE → **不覆盖 INSERT**；
    · trg_teachers_protect_last_super_admin = BEFORE UPDATE OR DELETE → **不覆盖 INSERT**。
    所以：**直接插入**一个 roles 含 super_admin 的新行是被允许的，不需要声明任何权限；
    而把已有账号**改成** super_admin 会被拒绝，除非在同一事务内声明
    select set_config(  app.rbac_actor_super_admin ,  on , true )（方案 B 已写明）。

  连接身份提示：表 owner（如 qlsadmin）不受 RLS 约束；受限角色走
  rls0004_anon_ins_teachers（INSERT 策略，角色 anon_）。建议用 owner。

  密码哈希：必须用第 3.1 节生成的完整 6 段字符串，格式
      scrypt$16384$8$1$<b64 salt>$<b64 derivedKey>
  手写/猜格式会静默走到 verifyPassword 的 return false（表现为"用户名或密码错误"）。

步骤 3.3 —— 用密码登录（此时 MFA 还没绑定，登录会成功并下发会话）

  因为该账号**尚未绑定 MFA**，auth.service.ts:443 的 `isEnabled()` 为 false，
  登录直接创建会话（不会返回 challenge），随后：
    · 认证通过（有会话 cookie）
    · 但 AuthGuard 因 roles 含 super_admin 而拒绝**非 @MfaExempt** 的请求 → 403
  这正是设计：强制 MFA 但允许自助绑定。

      curl -sS -c /tmp/qls-cookies.txt -X POST "${MFA_BASE}/api/auth/login" \
        -H 'Content-Type: application/json' \
        -H 'Origin: ${MFA_BASE}' \
        -d '{"username":"<登录名>","password":"<密码>"}'
  期望：HTTP 201，响应体为 {"mfaRequired":false,"teacher":{...}}
  ⚠️ 若返回 401 → 用户名或密码不对（或哈希格式不对，见第 5 节）；
     若返回 403「账号已锁定」→ 连续失败 5 次触发了 15 分钟锁定。

步骤 3.4 —— 自助绑定 MFA（**不要**手工写 teacher_mfa）

  开始绑定（返回一次性 secret 与 otpauth URI）：

      curl -sS -b /tmp/qls-cookies.txt -X POST "${MFA_BASE}/api/auth/mfa/enroll" \
        -H 'Origin: ${MFA_BASE}' -H 'Content-Type: application/json'

  期望：HTTP 201，返回 {"secret":"...","otpauthUri":"otpauth://totp/..."}
  → 把 secret 或 otpauthUri 导入认证器 App（Google Authenticator / 1Password 等）。
  ⚠️ secret 只返回这一次，且**不要**把它粘进任何日志、工单或提交记录。

  确认绑定（提交 App 当前显示的 6 位码）：

      curl -sS -b /tmp/qls-cookies.txt -X POST "${MFA_BASE}/api/auth/mfa/confirm" \
        -H 'Origin: ${MFA_BASE}' -H 'Content-Type: application/json' \
        -d '{"code":"123456"}'

  期望：HTTP 201，返回 {"recoveryCodes":[...]}（10 个，仅此一次）。
  ⚠️ 恢复码是凭据：立刻存入密码管理器。丢失 = 认证器丢失时无法登录。
  ⚠️ TOTP 有 ±1 步（±30 秒）时钟容差（mfa.service.ts:41 TOTP_WINDOW=1）；
     服务器时钟偏移过大会导致码一直不对，先确认时间同步。

步骤 3.5 —— 重新登录，验证第二因素真的生效

      curl -sS -c /tmp/qls-cookies2.txt -X POST "${MFA_BASE}/api/auth/login" \
        -H 'Content-Type: application/json' -H 'Origin: ${MFA_BASE}' \
        -d '{"username":"<登录名>","password":"<密码>"}'
  期望：HTTP 201，响应体是 {"mfaRequired":true,"challengeToken":"...","expiresAt":"..."}
        —— **不再**直接返回 teacher，也**没有**会话 cookie。

      curl -sS -c /tmp/qls-cookies2.txt -X POST "${MFA_BASE}/api/auth/mfa/verify" \
        -H 'Content-Type: application/json' -H 'Origin: ${MFA_BASE}' \
        -d '{"challengeToken":"<上一步的 token>","code":"<App 当前 6 位码>"}'
  期望：HTTP 201 且下发会话 cookie → 到此才算真正"可登录"。

5. 不要做什么（每条都有原因）
──────────────────────────────────────────────────────────────────────────────

  ✗ 不要把 __rbac_keeper（或任何 __ 开头的账号）当作生产账号使用。
    它是 tests/helpers/reset-fixtures.mjs 的夹具：`ensureKeeper()` 只写
    (username, name, name_en, roles, status)，**刻意不写 password_hash**，
    用途是在验证运行期间让"最后一个 super_admin 不可删除"的触发器可满足。
    给它补密码会让夹具行为偏离验证基线，掩盖真实问题。

  ✗ 不要手工拼或"猜" password_hash。
    登录校验（auth.service.ts:242-256）要求恰好 6 段：
      parts[0] === 'scrypt' 且 parts.length === 6，格式 scrypt$N$r$p$salt$dk
    任何格式偏差都会静默走到 `return false`，表现为"用户名或密码错误"，
    且会在审计里留下 login_failed —— 排查成本极高。必须用步骤 3.1 的应用同款参数生成。

  ✗ 不要手工写 teacher_mfa / mfa_recovery_codes。
    TOTP 密钥是 AES-256-GCM 加密后存储的（mfa-crypto.ts，格式 v1:<iv>:<tag>:<ct>），
    手工写就要自己复现整套加密，风险远高于走一行 API。而且**不需要**手工：
    @MfaExempt 的 enroll/confirm 端点就是为自助绑定准备的。

  ✗ 不要为了让事情"跑起来"而关掉强制 MFA 网关。
    auth.guard.ts:171-181 的检查是 super_admin 唯一的第二因素保障；
    mfa.service.ts:277-284 的 assertMayDisable() 也会拒绝解除绑定。
    关掉它等于把最高权限降级为单因素密码。

  ✗ 不要复用/提交任何生成的 secret、恢复码或密码哈希。
    MFA secret（3.4）、恢复码（3.4）、密码哈希（3.1）都是凭据。
    本脚本的输出里没有任何真实凭据，正是为了可以安全地贴进工单。

  ✗ 不要把 password_hash 复制到工单、聊天或提交信息里 —— 它是可离线爆破的物料。

──────────────────────────────────────────────────────────────────────────────
6. 【重要】MFA_ENCRYPTION_KEY 与单实例约束 —— 别在这一步把自己锁在门外
──────────────────────────────────────────────────────────────────────────────

  当前 shell 里的 MFA_ENCRYPTION_KEY: ★ 未设置

  这是整条流程里最容易造成"上线后无法登录"的一点，单独强调：

  · TOTP 密钥（含上面 3.4 绑定的那个）以 AES-256-GCM 加密存库，
    加密键来自 MFA_ENCRYPTION_KEY（mfa-crypto.ts:198-217，必须解码为恰好 32 字节）。
  · 因此：**如果你在绑定 MFA 之后重新生成这个键，已有的绑定会永久无法解密。**
    届时该账号登录会在 auth.service.ts:443 的 isEnabled() 路径上 FAIL CLOSED
    —— 表现为拒绝登录，而**不是**静默降级为单因素（这是刻意的安全选择）。
  · 正确做法：**先**生成一次、写进部署环境（.env.deploy / 平台环境变量），
    **再**开始 3.4 的绑定；此后永不更换。
  · 生成命令（只跑一次）：openssl rand -base64 32
  · 备份要求：与数据库备份**分开**保存。两者在一起等于没加密；
    只剩数据库备份而没有键，等于所有 MFA 账号一起失联。

  单实例约束（DEPLOYMENT_PRODUCTION.md 附录，正式架构前提）：
    · 登录限流是**进程内**计数 → 多副本会把实际上限乘以副本数；
    · 迁移用 advisory lock 串行；
    · 所以第一阶段必须单实例，`docker compose up` 不要 --scale app>1。
